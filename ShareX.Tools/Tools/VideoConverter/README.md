# Video converter

The window keeps settings and drag/drop actions disabled while choosing an input/output path or encoding. Commands and setters also check that state, so a delayed picker cannot start a competing conversion or change saved settings after close. Storage callbacks check closure again after resolving the suggested folder, before opening a dialog.

Each conversion retains its cancellation token until the handler actually completes. Stop cancels the current job and leaves editing disabled until completion; closing rejects further UI callbacks and cancels the job once. Queued progress is accepted only for the current, uncancelled job, so an earlier conversion cannot overwrite a completed result or a later job. Completion uses the output path captured in the conversion request.

`ShareX.Tools.Tests/VideoConverterLifetimeTests.cs` covers these paths with controlled picker/job callbacks, a queued synchronization context and fixture-owned temporary input files. It never invokes a media engine or a native dialog. The test project now targets plain `net10.0` (R21).

The converter accepts an optional `getSupport` callback alongside its opaque conversion handler. The application host supplies it through `ToolsIntegration` using the same captured FFmpeg executable path as the handler. Direct tasks also check the actual task's capture settings, with the existing default-settings fallback. The conversion worker checks cancellation and file-media support immediately before launching the engine and returns the translated reason when unavailable. Existing custom handlers remain compatible. The view model disables editing/pickers/start when unsupported, rechecks after picker completion and immediately before dispatch, and keeps Stop available for a running conversion after support loss.

`ShareX.Tools.Tests/FileMediaSupportTests.cs` adds controlled unsupported, late-picker, reentrant-dispatch and stop coverage. UI reasons reuse the translated FFmpeg-unavailable string without legacy installation advice. File tools remain independent of desktop recording support. R22 must still align Linux backends with the no-extra-installations scope; these checks do not establish Linux feature support or actual desktop verification.
